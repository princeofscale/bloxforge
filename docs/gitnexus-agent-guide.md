## Always Do

- **Run impact analysis before editing any symbol.** Before modifying a
  function, class, or method, run `impact({target: "symbolName", direction:
  "upstream"})` and report the blast radius (direct callers, affected
  processes, risk level). For unified PDG impact, add `mode: "pdg"` with
  optional `line: <N>` — it returns statement-level `affectedStatements` over
  CDG + REACHING_DEF and inter-procedural symbols in
  `interproceduralByDepth`/`byDepth`; no-layer/degraded PDG results are
  UNKNOWN-risk notes (`--pdg` layer).
- **Run `detect_changes()` before committing** to verify your changes only
  affect expected symbols and execution flows. For regression review, compare
  against the default branch: `detect_changes({scope: "compare", base_ref:
  "main"})`.
- **Warn the user** if impact analysis returns HIGH or CRITICAL risk before
  proceeding with edits.
- Exploring unfamiliar code: `query({search_query: "concept"})` instead of
  grepping — returns process-grouped results ranked by relevance.
- Full context on a symbol (callers, callees, which execution flows it
  participates in): `context({name: "symbolName"})`.
- "How does A reach B?": `trace({from: "...", to: "..."})` — shortest call
  path in one call instead of chaining `context`/`impact` hops by hand.
- Security review: `explain({target: "fileOrSymbol"})` lists taint findings
  (source→sink flows; needs `analyze --pdg`).
- Control/data dependence: `pdg_query({mode: "controls", target:
  "fileOrSymbol"})` answers "under what condition does X run?" (CDG, incl.
  guard clauses); `pdg_query({mode: "flows", target, variable})` traces
  "where does variable Y flow?" (REACHING_DEF). Both need the `--pdg` layer.

## Never Do

- NEVER edit a function, class, or method without first running `impact` on it.
- NEVER ignore HIGH or CRITICAL risk warnings from impact analysis.
- NEVER rename symbols with find-and-replace — use `rename`, which
  understands the call graph and produces confidence-tagged, multi-file edits.
- NEVER commit changes without running `detect_changes()` to check affected scope.

## Full tool reference

| Tool | Use for |
|---|---|
| `query` | Process-grouped code intelligence — execution flows related to a concept |
| `context` | 360-degree symbol view — callers, callees, processes it participates in |
| `impact` | Symbol blast radius — what breaks at depth 1/2/3, with confidence |
| `trace` | Shortest path between two symbols — "how does A reach B?" |
| `detect_changes` | Git-diff impact — what your current changes affect |
| `rename` | Multi-file coordinated rename with confidence-tagged edits |
| `cypher` | Raw graph queries (read `gitnexus://repo/bloxforge/schema` first) |
| `explain` | Persisted taint findings — source→sink data flows (`--pdg`) |
| `pdg_query` | Control/data dependence — what gates X (CDG) / where Y flows (REACHING_DEF) (`--pdg`) |
| `check` | Graph invariants such as circular imports |
| `route_map` | API route map — which components/hooks call which endpoints, and the handlers that serve them |
| `shape_check` | Response-shape drift — keys a route returns vs. keys its consumers access |
| `api_impact` | Pre-change report for an API route — consumers, middleware, shape mismatches, risk |
| `tool_map` | MCP/RPC tool definitions and the files that handle them |
| `group_list` / `group_sync` | Multi-repo group config / rebuild cross-repo contract links |
| `list_repos` | Discover indexed repos (paginated) |
